本项目启用全局自动化任务监督钩子。最终完成前必须具备：冻结的研究设计与数据 manifest、无泄漏管线及测试、可建模性审计、主比较的可复现结果、失败边界与数据路线图、执行对比报告及其表图和生成脚本。事件树的条件性分支若不满足开启条件，必须以有证据的“不启动”记录完成，而不是遗漏。

## 强制上下文重建

每当代理开始新的上下文、从摘要或压缩上下文恢复，或缺少当前工作状态时，必须在回答用户、提出计划、运行命令或修改文件前完整读取：

1. `whathappentov1.md`
2. `list.md`
3. `study_design.yaml`（若已创建）
4. `whatwedo.md`
5. `.log/plan.log`
6. `.log/terminal.log`
7. `.log/git.log`

将 `whathappentov1.md` 视为 v1 证据与 v2 研究边界，`list.md` 视为当前行动指南，`study_design.yaml` 视为冻结后的研究设计，`whatwedo.md` 和 `.log/` 视为最新状态。发生冲突时，以已经冻结的研究设计和本地状态记录为准，并先向用户说明。

只有在需要追溯 v1 数据语义、复用只读基线或核实既有结论时，才读取 `../PTMv1/ARCHIVE.md`、`../PTMv1/ENCODER_NECESSITY_REPORT.md`、`../PTMv1/whatwedo.md` 或其代码；不得修改 v1，也不得重新将其加入 Git。

## Git 原子提交规则

用户要求所有项目更改采用原子提交。每完成一次独立、可说明的文件修改后，必须：

1. 检查本次修改的 diff；
2. 只暂存本次涉及的明确文件，不使用宽泛暂存；
3. 用准确的提交信息创建 Git commit，并推送到 `vacuoleC/PTM`；
4. 确认工作区中没有因本次操作产生的意外未提交文件。

`.log/`、远程运行日志、原始数据和临时诊断产物由 `.gitignore` 保持本地。`whatwedo.md` 是受版本控制的研究账本：每一个独立的研究、代码、数据、结果或决策提交，必须与其对应的 `whatwedo.md` 事件记录在同一个原子 commit 中提交。正式、可复现的数值汇总、脚本与研究设计应按单一实验轮次原子提交。

## 任务连续性与切换点

Git 原子提交只是可审计的版本边界，**不是**对话、心跳或研究事件的结束边界。一个事件（例如 E2.2）可以、也通常应当包含多个代码、测试、结果和账本提交；每次提交并完成校验后，代理必须立刻检查该事件尚未完成的子步骤并在同一任务回合继续，不能把“已提交”当作停止理由。

只有下列情形可结束当前任务回合：事件达到预先定义的完成条件；状态已先写为 `blocked_*`、`complete*` 或 `paused`；或真实的上下文/时间上限要求切换。在最后一种情况下，必须先在 `whatwedo.md` 与三类 `.log/` 记录当前子检查点、剩余子步骤、精确恢复命令、运行作业状态和 Git 状态。随后恢复时从该检查点继续，不重复已完成的子步骤。

机器可读状态必须与实际情况同步：可继续时设 `automation_supervisor: active` 与 `automation_state: active`；需要用户信息或授权时先设 `automation_supervisor: paused` 与 `automation_state: blocked_<原因>`，再提出一个请求并暂停心跳；整个项目完成时先写 `automation_supervisor: paused` 与 `automation_state: complete`，再交付最终报告。Stop Hook 以该状态作为是否续跑的唯一依据。

## 本地行动日志规则

`.log/` 是 Git 忽略的追加式本地审计目录。每个行动周期都必须只追加、不得改写历史：

- `plan.log`：新计划、计划调整，或明确说明计划未变；
- `terminal.log`：执行过的终端/工具动作及关键结果；不得写入密码、令牌或其他敏感信息；
- `git.log`：暂存、提交、推送和正式产物变更；提交时必须写入 commit hash 与摘要。

在向用户报告前，先把本次计划、终端动作与 Git 状态追加到这三个文件。恢复上下文后先读完三个日志，再决定继续、重试或清理未完成动作。从本规则生效起，每一条新日志均以事件 ID 开头，以便与 `whatwedo.md` 的记录关联。

## 版本化工作记录、证据与事件树

`whatwedo.md` 是可审计的研究叙事，而不是待办清单。每个原子工作单元均以唯一事件 ID 记录；开始时可标记为 `进行中`，结束、失败、暂停或改道时必须更新为最终状态。每条事件记录必须包含：

1. **事件 ID、父事件、同级比较组与状态**；
2. **为什么做**：要回答的研究问题、前置证据或失败触发条件；
3. **怎么做**：数据版本、脚本/配置、分割与统计方法、必要的算力信息；
4. **结果怎么样**：量化结果、失败现象或尚未完成的原因；
5. **证据与决策**：对应的 Git 提交、日志事件 ID、表格、图像、测试或输出路径，以及由证据导出的下一步。

每一项量化结论必须附至少一个可复现的证据表或图；图必须由版本化脚本和明确的数据/配置生成，标明样本数、比较对象和不确定性（适用时）。没有数值图表价值的配置、重构或失败排查，应链接可信的 diff、测试输出或日志，而不是制作装饰性图片。

在规划阶段先在 `whatwedo.md` 维护事件树大纲。新发现的机会、异常、失败或替代路线必须作为新事件加入该树，注明父节点与“为什么新增”，不得从最终叙事中抹去失败分支。最终交付必须从版本化 `whatwedo.md` 与本地 `.log/` 重建：

- `outputs/reports/v2_execution_comparison.md`：纵向事件树、同级任务对比、关键决策与失败分支；
- `outputs/tables/v2_task_comparison.csv`：同级任务的目标、方法、数据、资源、指标、证据强度与结论；
- `outputs/figures/v2_event_tree.svg`（或 PNG）：事件树可视化；
- 生成上述产物的版本化脚本与数据摘要。

## 研究设计与配置

所有路径、随机种子、拆分数、过滤阈值、模型参数、进度频率和远程监控参数必须由 v2 的版本化配置文件管理；研究问题、主终点、主比较和推断规则先写入 `study_design.yaml` 再运行。不得用结果倒推目标标签、模型或是否报告某项探索性分析。

所有涉及标签的特征过滤、填补、缩放、降维、调参与校准必须只在训练折拟合。v2 的主线是小样本可建模性审计与低容量基线；t-SNE 只用于作图，UMAP 与多视图仅为预注册探索性比较，不能伪造跨数据集或跨条件的配对样本。

## 远程算力与外部资源

远程算力机只用于执行已在本地完成原子提交的代码。同步路径固定为本地 `D:\coding\PTM` → GitHub `vacuoleC/PTM` → 远程 `/data/PTM`。远程只能在 `/data/` 下读写项目，且只能使用既有 Conda 环境 `ptm-encoder`；不得创建、删除、更新或探测其他环境，不得进行破坏性系统操作。

远程结果先写入 `/data/PTM/outputs`，核验后通过 GitHub 同步回本地。若 Git 不可用，只可通过既有 SSH 在 `/data/PTM` 内原子传送已经本地提交并推送的明确文件清单；不得批量覆盖目录或同步未提交文件。

## 长任务监督钩子

凡预计超过普通交互命令时限的训练、置换、下载或数据构建任务，启动前必须：

1. 让脚本以带时间戳、`flush=True` 的进度行写入 stdout，进度频率来自配置；
2. 在远程将 stdout/stderr 重定向到 `/data/PTM/logs/<job>.log`；
3. 使用受配置控制的监控脚本读取新增日志，并将进度、失败或完成状态追加到本地 `.log/terminal.log`；
4. 任务完成后先核验 outputs，再创建正式的原子结果提交；不得重启状态未知的作业。
